# #014 — Finishing 0.6.0: the guard's own part, and the review's fixes

**Ticket:** `#24` · **Devlog:** `#19` · **ADRs:** 0005 (applied further), none new
**Date:** 2026-11-08

---

## The Problem

The finish ticket closes phase measure-trim. Three problems came up while finishing it.

**The reverse out-of-step.** Brigade's hooks refuse any key they don't know in
`.claude/workflow.json`, so that a typo fails loudly instead of quietly switching a rule off. The
shell guard loads that file on *every* shell command. So a project whose config is a release ahead
of its plugin (the owner ran `/update-workflow` and wrote a new key, but this machine still has the
older plugin) gets every shell command refused: `ls`, `git status`, everything. The project's
config is fine; the plugin just doesn't know it yet. It is the mirror of D11, where a newer plugin
meets an older config, and the spec left it to the owner.

**The review found the night half-frozen.** ADR 0005 says one frozen copy of the runner judges a
whole night. The hooks and the stop checks did read the copy. But the runner itself still read
three files from the *live* `tools/phase-run/` for each ticket: `settings.json`, the base list of
what a session may and may not run, and the two prompts that tell it what to do. A shell write to
those files mid-night would have changed the rules for every later ticket.

**Small defects** the run's own sessions had noted:
- a test override in a ticket body could name a path without saying why, though the spec asks for
  both;
- a ledger row written after a torn line (a writer killed halfway) was glued to it, and both were
  lost;
- a header comment in `ledger.mjs` still described the version #14 chose, not the one #25 built.

## The Solution

- **`hooks/workflow-config.mjs` `parseGuard`**: the guard's own part of the file (`version` and the
  `guard` section, its rules and wrappers), split out of `parseWorkflowConfig`, which now calls it.
  There is one guard parser, not two.
- **`loadJudgeGuard(root, env)`**: what the guard loads. It tries the full, strict load first. If
  that fails but the guard's own part parses, it returns the guard's rules and wrappers with no
  error, and the full fault as `elsewhere`. A missing runner copy, a file that isn't JSON, a wrong
  `version`, or a bad `guard` section still come back as an error, and the guard still blocks.
- **`hooks/guard-shell.mjs`** calls `loadJudgeGuard` instead of `loadJudgeConfig`.
- **`hooks/version-check.mjs` `configLine`**: at session start, if the hooks' loader refuses the
  file, one line says so: "Brigade's hooks can't read .claude/workflow.json: … Shell commands still
  run, but a phase run won't start until it is fixed; if the file is from a newer Brigade, update
  the plugin." It asks `loadJudgeGuard`, so for a fault the guard can't get past (in `guard`, the
  `version`, or broken JSON) it says the opposite: no shell command runs until it is fixed. It
  joins the version line when both apply, which is the usual case.
- **`template/tools/phase-run/run.mjs` `runnerFile(runner, name)`**: the one place a night reads
  `settings.json`, `ticket-prompt.md` or `fix-prompt.md`. With a run copy it is the copy's file,
  and with none (a dry run) it is the runner's own.
- **`tampering.mjs` `givesReason`**: an override line must hold a word besides the path, once list
  markers and punctuation are taken out. A line that only names the path lets nothing through, and
  the gate's output says so and shows a line that would.
- **`ledger.mjs` `appendRow`** reads the file's last byte, and starts a new line if it isn't one.
- The template's phase-run guide gained trim, the test override, the version stop and the two
  config-fault messages; the CHANGELOG, README, `plugin.json` (0.6.0) and the development history
  were brought up to the release.

## Why This Approach

The guard's job is to refuse dangerous shell commands. A key it has never heard of, in a section it
never reads, tells it nothing about which commands are dangerous, so refusing the shell over it
punishes the owner for updating in the "wrong" order. What it *does* read still has to be right: a
broken block rule could silently let a forbidden command through, so that still blocks.

The strictness moved to where it matters. A typo in `stopGate` or `phaseRun` changes how a night is
judged, and the stop gate (which only runs inside a phase run) and the runner's preflight still
refuse it. So a bad file can no longer stop the owner's day, and it still can't judge a night.

For the half-frozen night, the fix routes the reads through one function and pins it with a test
that scans `run.mjs`, like the existing test that walks the runner's imports to prove no gate reads
a receipt. A source scan is blunt, but the alternative is a test that runs a whole ticket.

## Alternatives turned down

- **Warn on unknown keys everywhere** (both loaders drop them with a warning). It is the simplest
  forward-compatible rule, but a typo like `unreadof` would then quietly disable a gate's skip. The
  owner chose the narrower rule.
- **Keep refusing, and only document "update the plugin first".** No code, but one wrong order
  still costs the owner every shell command until they find the cause.
- **Fix `finishBuilt`'s double result** (a failed `gh pr create` after a push lists the ticket
  twice in the report). The fix is small, but no test can reach it without a real GitHub. It is
  recorded in discovery 04's addendum instead of shipped untested.

## Real bugs found along the way

- **The finish's own review caught two of this ticket's bugs.** The startup notice first said
  "Shell commands still run" for every fault, even one in `guard` that blocks them. And an override
  line naming two files counted each file's letters as the other's reason. Both have tests now.

- **The live check's own fixture was wrong.** A guard rule written into JSON from a shell as
  `"^echo forbidden\b"` let `echo forbidden` run. In JSON, `\b` is the backspace character, not a
  regex word boundary, so the rule matched nothing. Running the hook directly against the file
  showed it; the code was right. It is now a line in the gotchas.
- **A scratch repo loaded with `--plugin-dir` has no `enabledPlugins` entry for Brigade**, because
  an install writes it, not setup. Without it the runner finds no catalog and writes no auto-update
  override. That is correct behaviour, and the live check had to add the entry by hand.

## What This Concretely Unblocks

- 0.6.0 can be released: the phase is reviewed and its hook changes were seen working in real
  Claude Code sessions.
- A future release can add config keys without stopping every shell command for anyone whose
  plugin is a version behind.
- A night is now frozen in full: what a session may run and what it is told come from the copy too.

## Run by hand

- After the release: `claude plugin marketplace update aceotopes`, `claude plugin update
  brigade@aceotopes`, then `/update-workflow` here, so this repo's own runner and guide move to 0.6.0.

## Assumptions made

- A guard fault means only `version` and the `guard` section. A broken `phaseRun.tampering` no
  longer blocks the shell (#20 had made it block on purpose). The tampering gate still reads its
  rules from the base commit and never fails open, which is where that safety lives.
- Any letter or digit left on an override line counts as a reason (`#31` does); the gate doesn't
  judge whether the reason is a good one.

## Common Questions

**Q: Why not make the guard ignore the whole config when it can't read it?**
A: Because "no rules" would wave through exactly the commands the project's rules exist to stop.
The guard still applies every rule it can read; it only stops treating the *rest* of the file as
its business.

**Q: In an interview, how would you describe this change?**
A: "Our validator was strict about the whole config file, and one consumer, the shell guard, ran it
on every command. A forward-compatible key from a newer version locked users out of their shell.
I scoped each consumer's validation to the part it actually reads: the guard validates its own
section, and the stricter consumers that judge correctness stay strict. The trade-off is that a
typo outside the guard's section no longer stops the shell, so we surface it at session start
instead."

**Q: Why does the runner read its prompts from the copy, if a session can't edit
`tools/phase-run/`?**
A: The Edit tool is denied there, but a shell command can still write a file. ADR 0005's promise is
that nothing written mid-night changes the rules for later tickets, and the base settings and the
prompts are rules: one says what a session may run, the others what it is asked to do.

**Q: What still hasn't been seen?**
A: A real 0.6.0 night (the runner taking its own snapshot, reading the version, running gates side
by side), a `--bg` resume keeping trim's flags, and auto-update firing by itself.
